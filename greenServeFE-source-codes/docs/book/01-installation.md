# Installation and First Run

## Building from source

The build repository contains the core executable and a Makefile.

The executable is assembled from main.c, lexer.c, parser.c, value.c, bytecode.c, compiler.c, and vm.c.

Run:

~~~text
make clean all
./greenServeFE --version
~~~

The current executable reports version 1.0.0.

## Running a source file

A program is passed directly to the executable:

~~~text
./greenServeFE file.gsve
~~~

The command line requires a .gsve extension.

## Diagnostics

There are two implementation diagnostics:

~~~text
./greenServeFE --dump file.gsve
./greenServeFE --trace file.gsve
~~~

Dump mode displays generated bytecode. Trace mode prints VM instruction execution while the program runs.

## First program

Create hello.gsve:

~~~gsve
print("Hello, greenServeFE");
~~~

Run:

~~~text
./greenServeFE hello.gsve
~~~

The show built-in is an alias for the same output operation:

~~~gsve
show("Hello from greenServeFE");
~~~

## Distribution installation

The public distribution repository is:

https://github.com/dominexmacedon-docs/greenServeFE-

A normal Linux installation can place the executable in /usr/local/bin.

Native shared modules can be installed under /usr/local/lib/modules and exposed with:

~~~text
export GREENSERVE_MODULE_PATH=/usr/local/lib/modules
~~~

The loader searches local module locations as well, but an explicit module path makes a system installation predictable.

## Installation verification

Use:

~~~text
make clean all
./greenServeFE --version
./greenServeFE docs/examples/01-hello.gsve
./greenServeFE docs/examples/10-while.gsve
~~~

If the executable fails to build, diagnose the compiler or source tree first. If the executable runs but a native import fails, inspect the shared library and module path separately.

## Release discipline

A release should test the exact executable and native packages that are distributed together. Do not combine a new executable with an old ABI-sensitive shared library without testing compatibility.
